# Gemma 4 12B as a local model: validation plan

Status (2026-11-12): **steps 1-5 done; results and next steps are in `docs/MODEL_COMPARE_PLAN.md`** (tool calling works with thinking off; eval 51/56 twice). Goal: find out whether Gemma 4 12B Q4_K_M works as a local model in this app (tool calling in multi mode), and whether it beats or matches Qwen3-8B (the current local default). Read `docs/PLAN.md` first (rules in section 2 apply: never read `.env`, test on :8010/:5180, don't touch user data, say exactly what was verified).

## What is known
- File: `models/gemma4-12b/gemma-4-12b-it-Q4_K_M.gguf` (7,121,861,440 bytes) from ModelScope `unsloth/gemma-4-12b-it-GGUF`. Other ModelScope repos with the same model: `bartowski/gemma-4-12b-it-GGUF` (Q4_K_M 7.66 GB), `ggml-org/`, `lmstudio-community/`, `AtomicChat/` (`gemma-4-12b-it-GGUF`). File integrity (loads in llama-server) **not yet checked**.
- Reported by third parties, **not verified by us**: tool calling works on this model (NobodyWho model card: 14/14 on Q4_K_M, in their runtime). Counter-reports: a page claims llama.cpp `--jinja` does not recognise Gemma 4's native tool-call format; llama.cpp issue #22786 (tool call returned as plain text); an April community guide said Homebrew llama.cpp lacked Gemma 4 fixes. Our llama.cpp: 0.9.0 (build 12110, commit cd959bae9, Homebrew). Whether these apply to us is the first thing to test.
- Earlier PLAN.md note ("Gemma has no native tool format") was about Gemma 3 and may not hold for Gemma 4.
- Machine: M1 Pro 16 GB. Model needs about 7-8 GB plus context (more than Qwen3-8B's ~6 GB). **Qwen3-8B llama-server (PID 7971, :8080) is the user's and was running at last check.** Do not kill it; ask the user to stop it (or confirm RAM is fine) before loading Gemma, or run Gemma on :8082 only if memory allows (check `vm_stat` / Activity Monitor). 
- Downloads need `make local-model CA_BUNDLE=ca.pem` (committed `ca.pem` = public system roots; the shell's `CURL_CA_BUNDLE` is company-only and breaks Python downloads). Verified with a direct `modelscope` run, not via the Makefile line.
- Qwen3-8B baseline (multi mode, mock live data): eval 34 -> 35 -> 39 -> 42 of 45 (noise about +-2), mean 10.9 s per answer; six demo questions 5 of 6 good. Llama 3.1 8B: about 3 of 6, 9-16 s. Results table to fill in: `docs/EVAL.md`.

## Steps
1. **Server check (no app code).** Start Gemma: `llama-server -m models/gemma4-12b/gemma-4-12b-it-Q4_K_M.gguf --alias gemma4-12b --jinja -c 8192 -ngl 99 --port 8082` (add `--chat-template-kwargs` only if Gemma has a thinking switch; check the log). Confirm it loads (watch RAM) and `curl localhost:8082/v1/models` lists it.
2. **Raw tool-call test (decisive).** `curl` `/v1/chat/completions` with one tool (e.g. `get_weather`/`write_itinerary`-like schema), a question that needs it, once non-streaming and once with `"stream": true`. Pass if the response has structured `tool_calls` (name + JSON arguments, `finish_reason` = `tool_calls`). Fail if the call appears as text in `content`. Also test `tool_choice: "required"` with a single tool (the app uses it to force `write_itinerary`; for Qwen/Llama a *named* choice was not enforced, required was).
   - If it fails: try a newer llama.cpp (`brew upgrade llama.cpp`; ask the user first) or another GGUF repo (bartowski/ggml-org) with its own chat template; if still failing, stop and record "not usable on our llama.cpp" in PLAN.md. Do not write a custom parser unless the user asks.
3. **Makefile entry.** Add a `gemma4` branch to the `LOCAL_MODEL` block (`MODEL_REPO = unsloth/gemma-4-12b-it-GGUF`, `MODEL_FILE = gemma-4-12b-it-Q4_K_M.gguf`, `MODEL_DIR = models/gemma4-12b`, `MODEL_ALIAS = gemma4-12b`, `MODEL_ARGS` as needed). Note `DEMO_ENV` in the Makefile hardcodes the Qwen URL/model; make it follow `LOCAL_MODEL`/`PORT` (or pass overrides) so `make demo-backend` can target Gemma. `make local-llm-info LOCAL_MODEL=gemma4` should print the right line. README: add Gemma to the "Other model" paragraph only if it is worth it after step 5.
4. **Adapter check via the app.** Own backend on :8010 (`make demo-reset demo-backend` with the Gemma env: `LLM_PROVIDER=openai LLM_BASE_URL=http://localhost:8082/v1 LLM_MODEL=gemma4-12b LLM_API_KEY=local LLM_TIMEOUT_SECONDS=300`, multi mode, mock live data, real onnx embeddings, `samples/`). Run `scripts/llm_check.py`, then the six demo questions (check-out + breakfast, 6 PM flight delayed, medication rules + verify badge, vegetarian places open now, add dinner 8 PM tomorrow, not-in-documents) with `scripts/chat_cli.py`. Fix only real adapter quirks (streamed `tool_calls`, missing ids, system-role handling: Gemma templates can reject a `system` role or require strict user/assistant alternation), each with a test in `backend/tests`.
5. **Eval.** `make eval EVAL_LABEL=gemma4-12b` (45 questions, ~10 min or more; Gemma is bigger so probably slower). Compare score and mean seconds to Qwen3-8B above; optionally `scripts/compare_modes.py <trip> --yes` (single vs multi) and `scripts/eval_retrieval.py` is unaffected (embedder is separate).
6. **Decide and record.** Add a "Gemma 4 12B" paragraph to PLAN.md Phase 4c section and a row to `docs/EVAL.md` with: raw tool-call result, six-question outcome, eval score, seconds per answer, RAM use, any quirks. Keep Qwen3-8B as default unless Gemma is clearly better (say, >= 44/45 or fewer wrong-citation/refusal errors at acceptable speed). Update `ca.pem`/README only if something changed. Commit on branch `dev`.

## Don'ts
- Don't read `.env`; tell the user which lines to change if the app (not :8010 test backend) should use Gemma.
- Don't start anything on :8000/:5173/:8080; stop only processes you started.
- Don't delete `models/gemma4-12b/` or the other model folders.
- Don't claim tool calling works until step 2 passes on our own server.
